01 — Project Plan

1. Problem statement

CGVAK's outbound motion depends on senior BDEs doing account research, judging whether an account is worth pursuing, deciding an angle, and writing the message. That work is slow, inconsistent between reps, and invisible — when a deal lands nobody can say which signal predicted it.

Sales Demand Gen360 industrialises the research-to-strategy half of that motion and leaves the judgment call with a human. The system produces an evidence-backed recommendation; a rep approves, edits, or rejects it with a structured reason. Those decisions become training data for targeting.

3. Scope

In scope (first build)

  • Account ingest and CRM de-duplication
  • Parallel research: company, decision-makers, signals
  • Evidence store with provenance and a signal lifecycle
  • Versioned Account Context
  • Six-dimension qualification with a configurable scoring model (MAN retained as a legacy view)
  • Strategy agent producing weighted per-persona threads
  • Outreach drafts (LinkedIn + email cadence) and Sales Prep artefacts
  • Automated evaluation before human review
  • Human approval gate with structured rejection reasons
  • Execution handoff to La Growth Machine
  • Engagement and outcome capture, additive CRM sync
  • Learning store (candidate patterns, reviewed before promotion)

Out of scope (explicitly, from the approach doc)

  • Fully autonomous outbound
  • Autonomous LinkedIn interaction beyond approved execution
  • Automatic strategy changes from small samples
  • Fine-tuning before sufficient evaluation data exists
  • Reinforcement-learning infrastructure
  • Large numbers of independent micro-agents
  • Automatic destructive CRM updates

4. Milestones

Milestones map onto the five gates in the approach document, plus a foundation milestone. A gate is a question a senior BDE can answer honestly about the system — not a ship date. Do not start milestone N+1 until gate N passes.

M0 — Foundation

Repo skeleton, Docker Compose (Postgres, Redis, API, worker, web), Alembic baseline, FastAPI app with health endpoint, Angular 17 shell with routing and an API service, config asset CRUD (org profile, ICP, service catalog, proof points, writing samples, sales rules, scoring config).

Exit: docker compose up gives a running API and UI; config assets can be created and read. No gate — this is plumbing.

M1 — Intelligence → Gate: can the system reliably understand an account?

Account ingest (single + CSV), CRM dedup, ICP pre-match. Parallel research across three domains. Evidence store with source, retrieval time, and observation date. Signal extraction into typed, confidence-scored signals linked to evidence. Signal lifecycle (discovered → validated → active → stale → expired) with per-type TTLs.

Gate test: run 20 accounts a BDE knows well. For each, the BDE marks every extracted signal correct / wrong / missed. Target: no fabricated signals, and the material ones are found.

M2 — Qualification → Gate: does it identify worthwhile prospects against a human baseline?

Context Builder producing a versioned, compressed Account Context. Six-dimension scoring (Fit, Opportunity, Buyer, Commercial, Intent, Engagement) rolling up to an Opportunity Priority. Scoring weights and band cut-offs live in a versioned config row, not a prompt. MAN available as an optional derived view.

Gate test: a senior BDE independently ranks 40 accounts into High/Medium/Low. Compare rankings. Target: strong agreement on the High band, and near-zero High-rated accounts the BDE calls Low.

M3 — Strategy → Gate: would a senior BDE agree with the recommended play?

Strategy Agent: persona × service weighting across every mapped buying-committee member, problem hypothesis, trigger, positioning, channel, CTA, and an explicit "avoid saying" list. Thread activation governed by the sales-rules thread cap.

Gate test: blind review of 30 strategies. The BDE marks each play "I'd run this" / "wrong angle" / "wrong person". Target: majority agreement on High-priority accounts, with the wrong-person rate near zero.

M4 — Content → Gate: would the BDE actually use the output?

Outreach Agent generating the whole arc of copy for each active thread — one draft per step of whichever LGM cadence the campaign selected. Gen360 does not author the cadence itself; touch count and timing belong to La Growth Machine, and Gen360 fills that sequence's variables. Sales Prep Agent producing elevator pitch, pitch structure, discovery questions, and objection pre-empts. Evaluation Agent (deterministic rules + LLM semantic checks). Human approval UI with approve / edit / regenerate / reject and mandatory rejection reasons — all valid before the sequence is enrolled, after which the copy is frozen on the LGM lead.

Also in M4: registering the LGM cadences in Settings and the drift guards around that registration, since nothing can be enrolled against an unverified mapping.

Gate test: approve-without-edit rate on the first 100 drafts. This is the metric that decides whether the system gets used or shelved.

M5 — Execution

La Growth Machine adapter: push an approved sequence, receive send status and engagement events via webhook. Contact verification enforced before any send. Additive, versioned CRM sync via MCP connector. Multi-thread coordination — a reply on any thread pauses the others pending review.

No separate gate; folded into gate 5.

M6 — Closed loop → Gate: does the system improve targeting and strategy over time?

Outcome capture (reply, meeting, opportunity, won/lost) attributed back to signals and strategy. Learning store recording candidate cross-account patterns. Nothing in the learning store changes production scoring or strategy without an explicit human review-and-promote step.

Gate test: after ~200 outreach threads, the learning store surfaces at least one pattern a BDE recognises as true and at least one they can refute — evidence the loop measures something real.

5. Sequencing note

M1 and M2 can partially overlap: the Context Builder can be stubbed to pass raw signals through while research is still being tuned. M3 must not start before gate 2 passes — a strategy built on mis-prioritised accounts is untestable, because you cannot tell whether a bad play came from a bad strategy or a bad account.

02 — Architecture

1. Governing principle

Claude reasons; the application governs.

Every business-critical decision point — workflow state, tool permissions, approval state, scoring weights, evidence records, audit logs, send authorisation — lives in the application and the database. Claude produces schema-constrained outputs that the application validates, stores, and acts on. A prompt can never grant a capability the application has not granted.

Two corollaries that shape everything below:

  1. The send capability is unreachable until a rep approves. Not "the prompt says don't send" — the Execution Adapter is a separate service that refuses any sequence whose approval row is missing or not approve.
  2. Nothing crosses a stage boundary as free text. Each stage's output is a typed record with a schema; the next stage reads that record, not the previous stage's prose.

How "must not" is enforced. These are not prompt instructions. Concretely:

  • Research agents get a tool set containing only web_search, web_fetch, and the contact-provider tool. There is no create_signal tool and no send tool in their scope.
  • Signal rows have a NOT NULL relationship to at least one evidence row, enforced by a service guard on write (a check constraint cannot span the join table, so this is a repository-level invariant with a test).
  • The Outreach Agent receives the strategy_thread record as its input contract; the evaluation step re-checks the draft against that record's positioning, cta, and avoid_list, and fails the draft on drift.
  • execution_record insert is gated by a query for an approval row with decision='approve' on the parent sequence. No approval, no insert, no API call to La Growth Machine.

5. Evidence and signal model

Every conclusion traces back to a date and a source:

Source + Date  →  Evidence  →  Signal  →  Conclusion
(where, when)     (stored,     (typed,     (what Qualification
                  not          confidence   and Strategy use)
                  interpreted)  -scored)

Reversible in the UI: click any conclusion and walk it back to the exact evidence it rests on.

Signal lifecycle. discovered → validated → active → stale → expired. Transitions:

From → ToTrigger
discovered → validatedEvaluation stage confirms evidence linkage and classification
validated → activeSignal is fresh (within its type's TTL) and used in the current context version
active → staleTTL elapsed, or a newer signal supersedes it (superseded_by)
stale → expiredHard expiry; the signal is retained for audit but cannot be cited

TTLs are per signal type and live in sales_rules.signal_ttl_days — a funding round stays relevant far longer than a job posting. A stale or expired signal cannot be cited as a trigger by a new strategy. This is checked at strategy-build time, not at review time.

Hypothesis tagging. Generated interpretations (problem hypotheses, persona-fit guesses, inferred org structure) carry is_hypothesis = true in storage and render with distinct styling in the UI. A hypothesis never silently hardens into a fact.

5.0 CRM is read first, before anything is spent

CRM lookup is the first research step, ahead of web research and well ahead of enrichment. The reason is economic and reputational: an account that is already a customer, or one CGVAK lost on price eleven months ago, should stop a cold campaign before a single token or enrichment credit is spent — and before a rep sends a "nice to meet you" opener to a company with an account manager.

CRM findings land as evidence with source_type='crm' and become ordinary signals. A prior lost deal is a Medium-strength prior_relationship signal, not a disqualification by itself; the rep decides. The Relationship card on Account Overview renders this, with a last-synced timestamp and a manual re-sync, because CRM data goes stale between runs.

Read-only inbound does not conflict with the additive-write-only outbound rule in §8.5 — those are different directions. Blocked on the custom CRM API spec (07 Q2); built against CrmAdapter with the stub in the meantime, exactly as the dedup path already is.

5.1 Company archetype detection

Before research fans out, the Context Builder classifies the account into one of six archetypes. This is not cosmetic: the same signal means different things at a 20-person startup and a 5,000-person enterprise, and searching for the same things at both wastes budget and produces noise. The archetype shifts what research looks for and how the qualification dimensions weight.

ArchetypeResearch emphasisWeighting shift
saasTech stack, integrations, ARR signals, engineering headcountIntent ↑
agencyClient roster, case studies, team size, service pricingCommercial ↑
ecommerceCatalogue size, traffic signals, platform, fulfilmentFit ↓ · Commercial ↑
enterpriseOrg structure, procurement, budget cycles, compliance needsBuyer ↑ · Timing ↓
smbOwner-operator signals, budget constraints, time-to-valueCommercial ↓
startupFunding stage, burn signals, growth trajectory, founding teamOpportunity ↑ · Engagement ↓

The weighting shift is a multiplier applied to the active scoring_config, stored alongside it and versioned with it — not a second scoring system. An account whose archetype is unknown scores on the base weights, and the low archetype_confidence is itself surfaced to the rep rather than hidden.

Archetype is stored on account, so a re-run that reclassifies an account is visible in the audit trail rather than silently changing its score.

Archetype set adapted from ai-sales-team-claude (MIT) — see docs/reference.

6. Qualification model

Six dimensions replace the single MAN score. MAN is retained as a derived, optional view for reps who still think in it.

DimensionQuestion it answersPrimary inputs
FitIs this the kind of company we sell to?ICP match, firmographics, industry, tech stack
OpportunityIs there a problem we can solve?Signals with a business implication
BuyerCan we reach someone who can say yes?Buying committee map, seniority, contact verification
CommercialCan they afford it and is the deal worth it?Funding, headcount, revenue band, spend proxies
IntentAre they showing active interest?Hiring, tech adoption, content consumption, inbound
EngagementHave we already got traction?Prior outreach, replies, meetings, CRM history

Roll-up: FIT + INTENT + TIMING + ACCESS → OPPORTUNITY PRIORITY (bands: Low / Medium / High). Weights and band cut-offs live in a versioned scoring_config row. The maths is deterministic Python, not an LLM call — the LLM produces per-dimension evidence-grounded assessments; the application computes the score. That keeps the model auditable and swappable, and makes re-scoring the whole book after a weight change a cheap batch job rather than thousands of LLM calls.

8. Memory architecture

Three stores, kept separate on purpose. Mixing them makes the system unable to distinguish "true for CGVAK" from "true for this account" from "true across many deals" — exactly the distinction Strategy and Qualification depend on.

StoreHoldsTables
Enterprise MemoryCGVAK's own facts — services, capabilities, ICP, industries, case studies, proof points, methodology, approved messagingorg_profile, service_catalog, proof_point, enterprise_memory
Account MemoryPer-account history — company facts, people, conversations, previous outreach, objections, responses, opportunities, historical signalsaccount_memory, plus the account-scoped operational tables

Retrieval uses pgvector embeddings on enterprise_memory and account_memory. Sales Learning is never retrieved into a prompt directly — a promoted learning changes a config value or a prompt template through a reviewed change, so its influence is explicit and reversible.

8.5 Selection layers — lists, queues, campaigns

Three labelled containers sit between an import and a send. Every boundary is a copy, not a link, and each one is a deliberate human act.

Account List ──copy──► Campaign Queue ──copy + lock──► Outreach Campaign
 (import set)          (mutable while draft)          (independent from here on)
LayerHoldsMutability
Account ListAccountsGrows by import or manual add. No filter, so no sync concept
Campaign QueueAccounts copied from one or more listsEditable while draft; locked on promotion
Outreach CampaignThreads (per contact) copied from one or more queuesIndependent once created

Why copy rather than link. A live link — where a queue is a saved filter recomputed on read — looks convenient and fails in four ways: research and drafting fire automatically on accounts nobody chose (cost); the Approvals inbox fills with drafts the rep never intended, polluting the M4 gate metric; "which accounts were in the September campaign?" stops being answerable, breaking §12; and an account dropping out of a filter leaves its already-running sequences orphaned — live outreach to a contact whose membership record says they were never there. Copying costs a manual rebuild and avoids all four.

To reuse a locked queue, clone it into a new draft. Re-opening a locked queue would make "which version did campaign 2 use?" unanswerable.

Two guards this design makes load-bearing:

  1. The thread cap goes global. With no cross-queue dedup, max_concurrent_threads is the only thing stopping two campaigns working one account simultaneously. It is enforced across all campaigns and checked at promotion, blocking with the conflict named — a rep can act on that; a silent send-time skip is invisible.
  2. A send-time safety interlock — the one deliberate exception to "nothing flows backward". Decoupling is right for convenience syncing, but taken literally it would let a company that landed on the no-go list yesterday keep receiving touches. Before each send the Execution Adapter re-checks: account not disqualified, not on the no-go list, contact not unsubscribed, email verified for email touches. Failure skips the touch. Nothing propagates back to the queue.

8.6 Cadence

Cadence structure belongs to La Growth Machine. Gen360 does not author, edit, or reorder steps — it selects one of a small set of pre-built LGM cadences and fills that cadence's variables. Touch count and timing are LGM's to decide. See Cadence ownership below for why, and Cadence registration for how the two systems stay in step.

Selection, not adaptation. Because each distinct set of day offsets would need its own LGM campaign, per-thread variation quantises to shape selection:

Condition on the account or contactShape selected
contact.email_status != 'verified'LinkedIn-only 5 / 15d
account.archetype = 'enterprise'Enterprise 8 / 23d
account.archetype = 'startup'Startup 5 / 11d
Medium priority bandNurture 4 / 21d
OtherwiseStandard 6 / 15d

Selection is deterministic Python reading sales_rules — no LLM. The earlier design for LLM-proposed cadence variation is dropped, not deferred: with structure owned by LGM there is nothing for it to propose.

Full storage: 03 — Domain 5c.

Content, as distinct from structure. The cadence governs when and which channel; the words come from each thread's own Strategy object, so the same cadence produces different copy per account. The whole arc is generated up front, approved once at sequence level, and written to the LGM lead at enrolment — after which it is frozen. See Content is frozen at enrolment below.

8.7 Manual intelligence

A rep knows things research cannot reach — what was said on a call, who the real gatekeeper is, that a competitor is already in the building. The system takes this as first-class evidence, not as a side channel.

The entry pattern mirrors everything else in the system: the human supplies knowledge, the model proposes structure, the human confirms. A rep writes plainly; the model returns typed signals with strength, confidence, business implication, and expiry; the rep unticks what they disagree with. This keeps signal typing consistent with researched signals — which matters, because the Learning layer compares signals across accounts and cannot do that if every rep invents their own vocabulary.

Three entry points, one component: account header, contact card, and thread detail. The third is the valuable one — learning something from a reply is exactly when a rep has new information and is already on that screen.

What must not happen: new signals on an account with an executing campaign flag, never rewrite — and in fact cannot rewrite it, since the copy is already frozen on the LGM lead. A new signal updates qualification and shapes the next campaign; the running sequence is unaffected. The rep's only lever over it is to stop it. The consequence is shown at the moment of saving: which of qualification, strategy, and cadence the new signal would change, with the rebuild left as the rep's decision.

9. Multi-thread coordination

An account rarely has one buyer. Strategy weighs every mapped persona and may activate several threads, capped by sales_rules.max_concurrent_threads.

  • Thread start times are offset so two contacts at the same company are not touched the same day.
  • A reply on any thread is visible across the account — the rep sees one account, not per-persona silos — and pauses the other threads' next touch pending review.
  • The thread cap is a sales rule enforced by the application, not a per-agent judgment call.

11.5 Learning is gated like everything else

The Learning layer is the last place a conclusion could enter production without evidence, and the highest-leverage one — a promoted pattern changes the scoring of every future account, not one message to one person.

So the same gate applies: a pattern cannot be promoted without the reviewer being able to open the cases behind it. The UI enforces this by making the drill-through the primary content of the pattern screen rather than an optional detail — supporting cases, counter-examples, and the evidence chips that lead to source excerpts.

12. Auditability

Every state transition writes to audit_log with actor type (agent / user / system), actor id, subject, and before/after payloads. Three questions must be answerable from the database alone, with no log-grepping:

  1. Why was this account prioritised? → qualification.reasons → signal → evidence
  2. Why did we say this to this person? → draft → strategy_thread → signal → evidence
  3. Who approved it, and did they change anything? → approval (+ edited_body)

Cadence ownership — settled with La Growth Machine

LGM owns the cadence. We own the words. Confirmed with LGM support, and it is not a preference — a cadence step cannot pull content from an external system at execution time. Webhooks are event notifications, not content providers. So content must exist on the lead before the campaign runs, which makes "generate the whole arc up front" mandatory rather than a design choice.

The mechanism

Each step in the LGM sequence inserts a variable — {{custom_attribute_N}} — that we fill per lead before enrolment. Cadence structure and timing live in LGM; per-touch copy comes from that thread's Strategy object.

Three consequences

1. Ten attributes per lead is a hard cap. A six-touch mixed cadence lands exactly on it, so email subjects use LGM's native variables ({{firstname}}, {{companyname}}) with per-shape templates, and our attributes are spent on bodies. That trades some subject-line personalisation for headroom.

We deliberately do not rotate a small pool of attributes to dodge the cap. Compare failure modes: with one attribute per touch, a failed rewrite sends the original human-approved content — stale but valid. With rotation, a failed rewrite sends touch 1's message again as touch 4 — visibly broken to the recipient. Safety beats capacity.

2. Adaptation quantises to fixed shapes. Continuous per-thread variation is not expressible, because each distinct set of day offsets would need its own LGM campaign. Layer 2 rules change from "stretch ×1.5" to "select the Enterprise shape":

ShapeSelected when
Standard 6 / 15ddefault
LinkedIn-only 5 / 15demail unverified
Enterprise 8 / 23denterprise archetype
Startup 5 / 11dstartup archetype
Nurture 4 / 21dmedium priority

Shapes are built and edited in LGM. Gen360 does not author cadences and cannot add, remove, or reorder a step — it adopts whichever cadence a campaign selects and fills that cadence's variables. Touch count and timing are LGM's to decide.

LGM can also create campaigns programmatically via its MCP server, but for five or six fixed shapes that is an integration dependency without a payoff — and a hand-built sequence has been looked at by a person.

3. Content is frozen at enrolment — this is the biggest constraint in the build.

All of a thread's attributes are written to the LGM lead before the campaign starts, in one batch. LGM's own guidance is to fill the attributes before the campaign runs. A lead-update path appears to exist, but it is not usable for timed mid-flight rewrites: LGM exposes neither the scheduled send time per step nor whether a step reads its attribute at step start or at send. Writing into an unverifiable window is not something to build a send path on.

Once a campaign is in motion, the words cannot change. A new signal, a manual note, a rebuilt strategy — none of it reaches a sequence already running. The only reliable in-flight control is stop: pause or remove the lead so the remaining touches never fire.

Two rules follow, and both are enforced at generation rather than left to chance:

RuleWhy
Early touches may anchor to signals; late touches must notTouch 6 is written on day 0 and sends on day 15. "12 open roles right now" may be false by then. Late touches use durable framing — capability, proof points, a soft close — so they cannot go stale. Enforced in the drafting prompt, checked by evaluation
An expiring signal stops the sequence, it does not rewrite itSending known-stale copy is worse than sending nothing. The thread returns to the rep

To change the words at all, a thread must be stopped and re-enrolled — a new enrolment writes a fresh set of attributes. That is a new sequence from touch 1, not a resume.

This also raises the stakes on the approval gate: since content cannot be corrected after enrolment, approval is genuinely the last point of human control. The sampling design in 05 should be read with that in mind.

What the Execution Adapter actually does

Not "send this message". Its job is: write attributes → enrol the lead in the right shape's campaign → manage lead status (pause, resume, remove) → consume engagement webhooks. It remains the only component with send capability, reachable only after approval.

Cadence registration — the contract between the two systems

Because LGM owns the cadence and Gen360 owns the words, something has to record which custom_attribute_N each LGM step reads. That mapping is the cadence_shape registration, and it is the most fragile joint in the system.

LGM's API does not appear to expose sequence structure, so registration is manual: someone records the LGM campaign id and its ordered steps in Settings → LGM cadences.

Drift is the failure mode

If a sequence is edited in LGM — a step added, channels reordered — and the registration is not updated, Gen360 writes copy into the wrong slots. Touch 3's message lands in touch 4's step, and neither system raises an error. The first sign is a recipient receiving something that does not follow.

LGM has confirmed the API cannot read sequence structure — no steps, shapes, or message templates. It can read campaign metadata and performance metrics. That is enough to turn a blind expiry timer into a change detector.

Checked automatically, hourly, from campaign metadata

CheckCatches
Campaign updated_at vs registration verified_atAny change to the LGM campaign after our last verification — blocks enrolment the same day rather than up to 90 days later
Declared channels vs registered channelsThe coarsest structural drift: a channel added or removed

Still requires a person

Step order, day offsets, and — most importantly — which attribute each step reads. A reordered sequence has identical metadata, so only a human comparison catches it. The part of the mapping that matters most is exactly the part the API cannot confirm.

A 90-day backstop expiry remains alongside the change detector, because updated_at is not confirmed to move when only a sequence body is edited. The detector is the primary guard; the timer is insurance against it being blind to body-only edits.

That last row matters: the durable-only cutoff is a function of how far ahead a touch is written, so it falls out of LGM's timing rather than being set independently. A 21-day nurture cadence pushes the cutoff earlier than a 11-day sprint.

Gen360's touch-performance analytics remain useful here, but only as evidence a human carries back to LGM. If touch 6 earns 3%, that is an argument for shortening the sequence in LGM — not something Gen360 can act on itself.

A second use for LGM's metrics: enrichment quality

LGM's campaign metrics expose bounce rate, which our own webhook stream does not reliably provide. That makes it the only honest read on enrichment quality — a bounce means an address a provider marked deliverable was not.

Attributed back to the provider and verification status that produced each address, it answers a question nothing else in the system can: are Apollo's "verified" emails actually verified? Early shape of the data supports the existing rule — risky-status addresses bounce several times more often than verified ones, which is why Sales Rules forbids emailing anything but verified.

This feeds the Learning layer as a provider-quality pattern, and it matters beyond one campaign: bounces damage sender reputation for every campaign that follows.

One campaign per contact — a hard constraint, not a policy

LGM has confirmed custom attributes are stored on the lead profile, shared across the account — not scoped per campaign. A lead has one CustomAttribute1, and every campaign that lead is in reads the same value.

So enrolling a contact in a second campaign overwrites the copy the first campaign is still sending. Mid-sequence, the remaining touches change subject to a different angle, referencing a conversation that never happened. Nothing errors in either system. The only person who finds out is the recipient.

Why LGM's two suggested workarounds don't apply

Their suggestionWhy it fails here
Use different attributes per campaignOur standard cadence uses 6 of 10. Two concurrent campaigns need 12. And campaign A's step 1 reading attr_1 while campaign B's reads attr_7 multiplies the registration-drift problem
Update the attribute before each campaign runsThat is the mid-flight rewrite ruled out by L1/L2 — and rewriting while campaign A still runs corrupts A. It only works sequentially, which is the constraint restated

The guard, and why account-level was not enough

The pre-existing check was the per-account thread cap. That is insufficient, because the cap counts threads on an account while the collision happens on a contact:

SituationThreads on accountWithin cap of 2?Collision?
Dana in campaign A, Marcus in campaign B2YesNo — different leads
Dana in campaign A, Dana in campaign B2YesYes — same lead

The second row passes the account cap and still corrupts. So a contact-level enrolment lock is required alongside it: a contact may hold at most one non-terminal sequence at a time.

Multi-threading within an account is unaffected — Dana and Marcus are different LGM leads with different attribute sets, so the persona multi-threading in the Strategy layer still works as designed.

Re-enrolment is ordered

Because the rewrite overwrites, changing a thread's copy must run in this order, and the order is enforced rather than advised:

  1. Stop the current sequence
  2. Confirm it is terminal — no unsent touches remain queued in LGM
  3. Write the new attribute values
  4. Re-enrol

Doing 3 before 2 corrupts the sequence still running.

Edge case worth handling in dedup

If LGM deduplicates leads by email or LinkedIn URL, one person is one lead even across two accounts. A contact who appears at two companies in our book would collide despite being two contact rows to us. The dedup logic should match on the same keys LGM does, not only on account_id + name.

Two things LGM does that change our capacity and safety assumptions

Daily action limits are shared per sending identity, not per campaign

LGM confirmed that concurrent campaigns share the sending identity's daily action limits, and the platform distributes actions between them. Throughput is therefore not additive: running three campaigns does not triple daily sends, it splits one allowance three ways.

The practical consequences:

  • Capacity planning is per sending identity, not per campaign. The Dashboard's send-capacity bars are correctly drawn as one allowance, and every executing campaign draws from it.
  • Launching a second campaign silently slows the first. Nothing errors — touches simply queue and roll to later days, stretching a 15-day cadence past 15 days.
  • Adding sending identities, not campaigns, is what raises throughput.

Because LGM decides the split, a campaign's real elapsed span is not knowable from its cadence alone. Progress must be read from actual send events rather than projected from day offsets.

LGM stops a lead across campaigns on reply or opt-out

If a lead replies or opts out in one campaign, LGM halts automation for that lead in every campaign under the same sending identity. That is a genuine safety net beneath our own rules — even if our contact lock were bypassed, a reply would stop the rest.

It is not a replacement for our rule, because the scopes differ:

RuleScopePurpose
LGM'sThe same lead, across campaigns on one identityStops contradicting yourself to one person
OursOther contacts at the same accountStops the account being worked while a conversation is live

Ours is the wider net and the one that protects the account relationship; LGM's protects the individual. Both are wanted, and neither makes the other redundant.

PostgreSQL 16 with the pgvector extension. All tables carry id UUID PRIMARY KEY DEFAULT gen_random_uuid(), created_at TIMESTAMPTZ NOT NULL DEFAULT now(), and where mutable, updated_at TIMESTAMPTZ. Those three columns are omitted from the listings below.

  • Enum-like columns are stored as TEXT with a CHECK constraint, not PG ENUM types — adding a value to a PG enum is a migration; adding one to a CHECK is a one-line ALTER.

Domain 5b — Selection layers (lists → queues → campaigns)

The three labelled layers between an import and a send. Each boundary is a copy, not a link. That is the defining property of this design and the reason there is no sync machinery anywhere in this domain.

account_list ──copy──► campaign_queue ──copy + lock──► outreach_campaign
                       (mutable while draft)           (independent from here on)
  • Building a queue copies account rows in. New imports into the source list never appear in the queue; status changes there never propagate. The source_list_id recorded on each member is a provenance stamp only — a dead reference kept for "where did this come from", carrying no behaviour.
  • A queue is editable while status = 'draft': add from any list, remove members.
  • Promotion locks the queue (status = 'locked') and copies its members' strategy threads into the campaign. To make a variant, clone the queue into a new draft — never re-open a locked one, or "which version of the queue did campaign 2 use?" stops being answerable.
  • Nothing flows backward. Campaign progress, replies, and outcomes have no bearing on the queue.

Learning patterns carry evidence, like every other conclusion

A pattern is a conclusion, and the system's founding rule is that every conclusion traces to dated, sourced evidence. A pattern with no traceable path back is the one place that rule could quietly break — and it is the most dangerous place for it to break, because promoting a pattern changes how every future account is scored.

The chain a reviewer can walk, entirely in the UI:

Pattern  →  supporting and counter cases  →  each case's signals  →  each signal's evidence
                                                                     → source, date, excerpt

Three requirements follow, and none is optional:

  1. Counter-examples are mandatory, not a courtesy. counter_case_ids is NOT NULL because a pattern presented without the cases where it failed is cherry-picking. 34 supporting against 11 counter is a finding; 34 against 40 is noise wearing a percentage.
  2. Confounders are computed and shown. If 29 of 34 supporting cases share one archetype, the pattern may be an archetype effect rather than a signal effect. The system detects the concentration and says so — it does not need to resolve it, only to stop a reviewer promoting blind.
  3. Promotion can be scoped. promotion_scope lets a SaaS-derived finding be promoted to SaaS accounts only, rather than applied globally to enterprise accounts the evidence never covered.

Promotion is not the end

post_promotion_lift re-measures a promoted pattern against accounts seen since promotion. A claim that drifts materially from its promoted value becomes a demotion_candidate. Without this, a promoted pattern is a permanent unexamined assumption baked into scoring — which is precisely what the evidence model exists to prevent.

A consequence worth stating in the schema

Because content is frozen at enrolment, draft rows for an enrolled sequence are immutable. There is no "edit the draft for touch 5 while touches 1–4 have sent" path — that would silently diverge from what LGM will actually send. Editing means stopping the sequence and re-enrolling, which creates a new outreach_sequence with new draft rows.

Enforce it: a trigger or repository guard rejecting UPDATE on draft where the parent sequence status is executing. Without it, the UI and LGM drift apart and nobody notices until a recipient gets copy nobody approved.

Enforcing the contact enrolment lock

Because LGM stores attributes per lead, two non-terminal sequences for one contact will corrupt each other's copy. This invariant is too consequential to leave to application logic — it belongs in the database, on a column that matches how LGM decides two records are the same person.

Key on LGM's identity, not ours. An index on contact_id has a hole: if LGM collapses two of our contact rows into one lead, both pass the index and still overwrite each other's attributes.

LGM confirmed it deduplicates on a priority cascade, not a single field:

PriorityIdentifierBehaviour
1LinkedIn URLSame profile → same lead, whatever the email
2EmailUsed when no LinkedIn URL. Same email → same lead even across different companies
3First + last + companyUsed only when neither LinkedIn nor email is present

A single computed column cannot express this, and assuming it could was wrong. Consider:

  • Contact A — LinkedIn X, email E1
  • Contact B — no LinkedIn, email E1

Keyed on a coalesce cascade, A resolves to X and B to E1 — different keys, so a unique index admits both. LGM matches B against A's stored email and merges them into one lead. The two sequences then overwrite each other's attributes, which is exactly the state the lock exists to prevent.

lgm_identity

Resolution therefore needs its own table, clustering contacts the way LGM would:

ColumnTypeNotes
idUUID PK
linkedin_slugTEXT UNIQUENormalised — host, casing, and trailing slash stripped

name_company_keyTEXT UNIQUE`lower(first \\last \\company)`, the fallback only

contact.lgm_identity_id FK. Resolution runs before enrolment and matches on any identifier in LGM's priority order: find by linkedin_slug, else email, else name_company_key; attach if found, create if not.

When a contact matches two different identities on different fields — A by LinkedIn, B by email — the row is marked conflict and enrolment blocks. LGM's own behaviour in that case is undocumented, so guessing which record it merges into risks corrupting whichever sequence guessed wrong.

CREATE UNIQUE INDEX one_active_sequence_per_lgm_identity
  ON outreach_sequence (lgm_identity_id)
  WHERE status IN ('pending_approval', 'approved', 'executing', 'paused');

A second contact resolving to an identity key already held by a live sequence is not always a duplicate — it can be a genuine fractional executive at two accounts, or a data error. Both cases surface at campaign pre-flight rather than being silently merged.

A partial unique index makes the bad state unrepresentable. A race between two concurrent campaign promotions cannot slip through, and no future code path can bypass it by forgetting a check.

outreach_sequence.status therefore needs a clean terminal/non-terminal split:

Non-terminal — holds the lockTerminal — releases it
pending_approval, approved, executing, pausedcompleted, stopped, cancelled

paused deliberately holds the lock: a paused sequence still has unsent touches whose copy sits in the lead's attributes. Releasing on pause would let a second campaign overwrite them.

04 — API Surface

FastAPI, mounted at /api. Every router is a module under app/api/. Pydantic v2 schemas live in app/schemas/, one module per domain.

Conventions:

  • List endpoints accept ?limit=&cursor= and return {items: [...], next_cursor: str|null}.
  • Long-running work never blocks a request. Those endpoints return 202 {run_id, status: "queued"} and the client polls GET /runs/{id}.
  • Mutating endpoints that cross a governance boundary (approve, execute) require an explicit reviewer_id from the authenticated session — never from the request body.

Learning — pattern detail

The screen exists to make a pattern falsifiable before it is promoted. Order matters: the maths, then the claim in plain language, then the confounders, then the cases — supporting and counter — then what promotion would change.

  • Four stat tiles: lift, supporting count, counter count, confidence against the promotion bar. Counter-example count is styled as a warning, not a neutral figure — it should feel like something to look at.
  • The claim in prose, precise enough to be falsifiable: rates, window, date range, population.
  • Confounder panel in amber when a concentration is detected ("29 of 34 supporting cases are SaaS"). It does not block promotion; it stops promotion happening blind.
  • Two case tables, both with evidence chips opening the same side panel used on the account screens. The counter-example table carries a "plausible reason" column — an enterprise account that never replied to a 6-touch cadence is a cadence finding, not a signal failure.
  • Promotion preview as a config diff, with Promote, scoped offered alongside Promote globally when confounders suggest the finding is narrower than it looks.
  • Post-promotion measurement, so a promoted pattern stays under review rather than becoming a permanent assumption.

Import is not a file picker. It is a dry run you confirm.

4. Structured output pattern

Every non-research stage follows the same shape. Pydantic model in, validated object out:

from pydantic import BaseModel, Field
from typing import Literal

class ExtractedSignal(BaseModel):
    signal_type: Literal["funding", "engineering_scaling", "hiring", "leadership_change",
                         "tech_adoption", "expansion", "m_and_a", "layoff",
                         "product_launch", "regulatory"]

    business_implication: str
    strength: Literal["low", "medium", "high"]
    confidence: float = Field(ge=0.0, le=1.0)
    observed_at: str                 # ISO date
    evidence_ids: list[str] = Field(min_length=1)   # never empty
    is_hypothesis: bool

    signals: list[ExtractedSignal]

response = client.messages.parse(
    model="claude-opus-5",
    max_tokens=16000,
    thinking={"type": "adaptive"},
    output_config={"effort": "medium"},
    system=SYSTEM_BLOCKS,            # cached — see §5
    messages=[{"role": "user", "content": evidence_digest}],
    output_format=SignalBatch,
)

evidence_ids having min_length=1 is the schema-level half of the "no signal without evidence" invariant. The repository guard is the other half — the model can still name an id that does not exist, so the service layer resolves every id against the evidence table and drops any signal citing an unknown one, logging it as an evaluation failure.

That drop-and-log behaviour is deliberate: a hallucinated citation is the single failure mode that would destroy rep trust, so it fails closed.

5. Prompt caching

Caching is the largest cost lever and it is free. The render order is tools → system → messages; any byte change invalidates everything after it.

Structure every call as:

[ tools           ]  ← deterministic order, never sorted differently between calls
[ system block 1  ]  ← CGVAK org profile + ICP           ] cache_control: ephemeral
[ system block 2  ]  ← service catalog + approved proofs ] cache_control: ephemeral
[ system block 3  ]  ← stage instructions + writing samples ] cache_control: ephemeral
[ messages        ]  ← the per-account context (volatile, uncached)

The first three blocks are identical across every account in a batch — that is the whole point. Serialise config JSON with sorted keys and no timestamps, or the cache silently never hits.

Verify, don't assume: log usage.cache_read_input_tokens on every call. If it is zero across repeated runs, a silent invalidator is present (a datetime.now() in a prompt, an unsorted dict, a tool list built from a set).

Max 4 cache breakpoints per request.

7.2 Objection pre-empt frameworks (Sales Prep)

The Sales Prep Agent generates two response shapes per objection so the rep can pick what fits the moment. Both are constrained the same way: every claim of outcome must cite an approved proof_point, and a draft citing an unapproved one fails evaluation.

Feel · Felt · Found — for emotionally-loaded objections (price, risk, change fatigue): acknowledge the concern genuinely, reference a comparable company that felt the same, then give the specific outcome they found. The "found" half must carry a real number or concrete result; "they loved it" is a failed generation.

Acknowledge · Bridge · Close — for tactical objections (incumbent tool, build-vs-buy, timing): validate without starting on "but", reframe the concern as a reason to move rather than dismissing it, then propose one specific next step.

Response length target is 3–5 sentences — roughly 15–25 seconds spoken, because these are said out loud on a call, not read.

7.3 When cadence content is generated

The cadence template is a skeleton — when, which channel, what the touch is for. The words are generated per thread from that thread's own strategy_thread record (problem hypothesis, trigger signals, persona, positioning, CTA, avoid-list) plus the account's context. Two accounts running the same template get entirely different copy; the template contributes structure, never content.

Neither extreme works for when to generate:

ApproachWhy it fails
All touches up front, never revisitedBy day 15 a draft may cite a signal that has gone stale, or a proof point since un-approved
Generate each touch at send time6 approvals per thread × 24 threads = 144 review actions. The rep stops using the system, which destroys the M4 gate metric

The model: generate the arc, approve once, re-validate before each send.

  1. Generate the whole arc up front. All touches are written in one pass when the sequence is created, in a single request per thread — so the model can see the arc and avoid repeating itself across touches. Cheaper too: the campaign and config prefix is cached, and only the per-thread context is uncached.
  2. Approve once, at sequence level. One approval covers the arc. The rep sees the whole progression, which is also the only way to judge whether touch 5 earns its place.
  3. Re-validate immediately before each send — a cheap low-effort call plus deterministic checks, returning a FreshnessVerdict:
CheckVerdict
Cited signal still active (not stale/expired)Fail → stop the sequence
Cited proof points still is_approvedFail → stop the sequence
Contact still verified for this channelFail → skip that touch (send-time interlock, 02 §8.5)
Reply received on any thread for this accountPause — existing cross-thread rule
New higher-strength signal appearedFlag for the rep; the running sequence cannot be edited
  1. Stop, never rewrite. Content is frozen on the LGM lead once enrolled, so a failed check cannot regenerate the touch in place. It halts the remaining touches and returns the thread to the rep, with outreach_sequence.stop_reason recording why. Changing the words requires stopping and re-enrolling — a new sequence from touch 1.

Cost. A 24-thread campaign at 6 touches is 144 drafts, but they are 24 requests (one per thread), not 144, and share a cached prefix. Sequence generation is a good Batch API candidate — it is not latency-sensitive and runs at 50% cost. Pre-send re-validation runs at low effort against a small payload, so it is negligible per touch.

7.4 Structuring manual intelligence

A rep's free text is converted to typed signals by the same SignalBatch contract used for researched signals. Using a separate schema would let manual signals drift into their own vocabulary, and the Learning layer's whole job is comparing signals across accounts.

Three constraints on this call:

  1. It proposes; it never writes. The endpoint returns candidates for the rep to confirm.
  2. Confidence is high by construction — a rep reporting a conversation is a better source than an inferred web signal. But is_hypothesis still applies to anything the rep framed speculatively ("I think they're probably...") and the prompt must preserve that distinction rather than flattening it into fact.
  3. Expiry is proposed, not assumed. "Decision by Q1" carries a real expiry; "they use Terraform" does not. Getting this wrong means stale signals drive live campaigns, which §7.1 rule 2 exists to prevent.

medium effort — this is a constrained transformation of text the human already wrote, not open reasoning.

L4 — can LGM's sequence structure be read programmatically? Answered: no

LGM confirmed the API exposes campaign metadata (name, description, status, channels, audience, timestamps) and performance metrics (open, reply, bounce rates, steps completed) — but not the sequence graph: no steps, shapes, or message templates.

  • Cadence registration stays manual, and step-level accuracy can only be confirmed by a person.
  • Metadata gives a real change detector — updated_at against verified_at — replacing a blind 30-day timer with same-day detection, plus a 90-day backstop for body-only edits the timestamp may not reflect.

  • Separately, bounce rate from the metrics endpoint became the enrichment-quality signal we were otherwise missing.

L3 — answered: attributes are global to the lead

LGM confirmed custom attributes live on the lead profile and are shared across the account. There is no documented mechanism for per-campaign values.

The conservative assumption turned out to be right, so nothing built on it needs revisiting. What changed is that the contact-level enrolment lock moved from prudent to mandatory, and it is now enforced by a partial unique index rather than application logic — see 03.

LGM suggested two workarounds; neither survives our cadence lengths. Using different attribute ranges per campaign needs 12 of 10 attributes and doubles the registration-drift surface. Updating attributes before each campaign runs is the mid-flight rewrite already ruled out by L1/L2.

All four LGM questions are now closed. L1 and L2 by design, L3 and L4 by answer. The remaining unknown is narrower: whether campaign updated_at moves when only a message body is edited, which determines whether the 90-day backstop is redundant or load-bearing. One test campaign answers it.

L5 — LGM's deduplication key — answered

A priority cascade: LinkedIn URL → email → first + last + company. First match merges the import into the existing lead. Same email means same lead even across different companies.

This broke the assumed key. I had assumed email-only, reasoning that stricter was safer. It was wrong in a way that mattered: LinkedIn ranks above email, so two contacts sharing a LinkedIn profile but holding different emails resolve to different keys under a single-column scheme while LGM merges them into one lead. The fix is a real lgm_identity resolution table matching on any identifier — see 03.

Also confirmed, and load-bearing: deduplication prevents duplicate profiles, not duplicate campaign membership. LGM will happily run one lead in several campaigns at once. Our contact lock is the only thing preventing it, which settles any question of whether it earns its complexity.

Two further findings, both from the same exchange:

  1. Concurrent campaigns share the sending identity's daily action limits — throughput is not additive, and a second campaign silently stretches the first.
  2. A reply or opt-out stops that lead across every campaign on the same identity — defence in depth beneath our own cross-thread pause.

Both are written up in 02.

Remaining unknown: what LGM does when a new import matches one existing lead by LinkedIn and a different one by email. Undocumented, so lgm_identity.resolution_state = 'conflict' blocks enrolment rather than guessing.
